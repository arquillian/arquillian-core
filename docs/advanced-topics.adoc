== Advanced Topics

=== Debugging

If you are struggling with running your Arquillian test and you need more info about what is going on underneath, then you can specify `-Darquillian.debug=true`. Arquillian will print out its lifecycle so you will know exactly where it got stuck.
The output has four types of information - you can distinguish them by their prefix:

* (E) Arquillian event that was fired
* (I) Arquillian interceptor that observed the related event context
* (O) Arquillian observer that observed the related event
* (X) Arquillian extension that was registered


=== Test Observer

In case you need to add an additional logic to the whole test suite, you can use Arquillian SPI and create your own Arquillian extension. But this extension is applied to all test classes.
In case you want to add an additional observer that will be applied only to one specific test class, then you can use an annotation `@Observer` at the test class level. This will use the specified class(es) as Arquillian observer(s) and observe any Arquillian event in the context of the related test class that you need (starting with `BeforeClass` and ending with `AfterClass`):

[source,java]
----
// JUnit Jupiter (JUnit 5 and 6)
@ExtendWith(ArquillianExtension.class)
@Observer(MyObserver.class)
class MyTestCase {

// JUnit 4
@RunWith(Arquillian.class)
@Observer(MyObserver.class)
public class MyTestCase {
----

The Arquillian observer class has to have a non-parametric constructor and the observer method should be defined by `@Observes` annotation:

[source,java]
----
public void observeBeforeClass(@Observes BeforeClass event) {
    ...
}
----

=== Parallel Test Class Execution

[IMPORTANT]
====
Experimental. Only some container types work with it, and both the configuration parameter and its behaviour may
change.
====

Arquillian normally builds one `Manager` for the whole JUnit run, firing `BeforeSuite` and `AfterSuite` once for
that run. That model cannot run test classes in parallel, because a manager's context activations are
thread-local. On JUnit Jupiter, the configuration parameter `arquillian.junit.jupiter.manager.scope` can be set
to `class` instead of the default `suite`, giving each top-level test class its own manager, shut down as soon as
that class finishes. A `@Nested` class shares its enclosing class's manager. Any other value fails the run.

Class scope only makes concurrency safe — Jupiter still has to be told to run classes in parallel, and that takes
*two* settings: `junit.jupiter.execution.parallel.enabled` turns the parallel executor on, and
`junit.jupiter.execution.parallel.mode.classes.default` decides what it does with test classes. Setting only the
second has no effect. All three go in a `junit-platform.properties` file on the test classpath, or in Surefire's
`configurationParameters`:

[source,properties]
----
arquillian.junit.jupiter.manager.scope = class
junit.jupiter.execution.parallel.enabled = true
junit.jupiter.execution.parallel.mode.classes.default = concurrent
----

Whether this works depends on the container. Embedded containers on ephemeral ports are the case it exists for:
each class gets its own instance with no collisions — for embedded Jetty that means `bindHttpPort=0`, together
with https://github.com/arquillian/arquillian-container-jetty/pull/257[arquillian-container-jetty#257]. Remote
containers started outside Arquillian work too, but the classes share one server, so anything with server-wide
identity (a JMS topic, a fixed deployment name) has to be made unique per class. Managed containers *will not
work*: concurrent `StartContainer` calls conflict over ports and resources. A container implementation could in
principle handle that, but none does today — and a managed and a remote container cannot be configured together
anyway (https://github.com/arquillian/arquillian-core/issues/866[issue #866]).
